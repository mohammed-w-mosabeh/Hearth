# Hearth — Security (NON-NEGOTIABLE)

Hearth is effectively a root-capable control panel. Assume any web page the user visits, any device on the same network, and any string coming from the system (container names, labels, package descriptions, file names) can be hostile.

## Assets
1. Root on the machine (including Docker socket = root).
2. User files, secrets in container env vars, Hearth DB.
3. System stability (no accidental removal of critical packages/services).

## Invariants

### Network & web
- S1. Hearth never listens on anything but 127.0.0.1; there is no LAN listener. Port chosen at first run, stored in config.
- S2. Launch token: 32 random bytes from `crypto/rand`, stored in `$XDG_CONFIG_HOME/hearth/token` mode `0600`, rotated on each hearthd start and **single-use**: a successful exchange burns it and writes a fresh one. The launcher opens `http://127.0.0.1:<port>/auth?t=<token>`; the server redirects (`303`, `Cache-Control: no-store`) to `/#k=<session key>` (fragment, never sent to a server). The UI keeps the key in `localStorage` (isolated per origin incl. port), removes it from the URL, and sends `Authorization: Bearer <key>` on API calls and `Sec-WebSocket-Protocol: hearth.v1, hearth.key.<key>` on WebSocket upgrades (server echoes only `hearth.v1`). **No cookies**: browsers send cookies to every port on the same host, so any other local web service (e.g. a container on `127.0.0.1:8080`) would receive them. Sessions live in memory as SHA-256 hashes, at most 16, and all end when hearthd restarts. The launcher opens the URL through the desktop portal; the token never appears in process arguments of transient units, unit descriptions or logs.
- S2a. Read-only tokens (v1.3): for the `hearth` CLI and `/metrics`, separate from the session key; a 0600 file the user creates and revokes on the Tokens page, on the same loopback listener. A read-only token can never call a state-changing route or a WebSocket action, tested on every route. A token reaches a closed list of whole GET paths and nothing else, not every GET, because some GETs open shells, export settings, quote logs or probe the network: `/api/v1/session`, `metrics/live`, `net/sockets`, `alerts/events`, `services` and `containers`, the last a brief list without command lines or mounts. Any `Upgrade` header is refused. Each token is 32 random bytes in `$XDG_CONFIG_HOME/hearth/tokens/<name>.token`, mode 0600 in a 0700 directory, and those files are the only record: hearthd keeps hashes in memory, nothing goes into the database, so no copy of it can carry a token or bring back a revoked one, and no API returns a token. A file that is a link, not a token or readable by others is ignored and logged, and never replaced. Names are 1–32 of `[a-z0-9-]`; at most 16 tokens. Creating and revoking are audited; revoking takes effect at once. `/metrics` is off until the user turns it on, is not in exported settings, answers a read-only token only (not a session key), checks the token before saying whether it is on, and adds no sampling; system strings travel only as escaped label values. The `hearth` command is a separate unprivileged binary: GET only, to 127.0.0.1 only, no proxy, no redirects, it refuses a token file others can read, and it replaces control and format characters in what it prints, so a container name cannot drive the terminal.
- S3. On every request: `Host` must be exactly `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding). On every non-GET request and every WebSocket upgrade: `Origin` must match. Reject otherwise with 403.
- S4. Headers: `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`.
- S5. Rate limit state-changing endpoints (e.g. 20/s burst 40). Request body limit 1 MiB (uploads 5 MiB, icons only, sniffed as PNG/SVG-sanitized/WebP).
- S6. No `{@html}` in Svelte, no `innerHTML`. Uploaded SVG icons are rasterized or sanitized server-side; served with `Content-Type: image/svg+xml` + CSP sandbox.

### Execution
- S7. No shell, ever. No `sh -c`, `bash -c`, `system()`. `os/exec` only in `internal/safeexec` with absolute-path allowlist and per-argument validators. CI lint fails otherwise.
- S8. Validators: Debian package name `^[a-z0-9][a-z0-9+.-]+$`; systemd unit name per `systemd.unit(5)`; container/image IDs `^[a-f0-9]{12,64}$` or validated refs; paths cleaned, absolute, and checked against allowed roots. Arguments starting with `-` are rejected where a name is expected.
- S9. Prefer D-Bus APIs over CLIs (systemd, PackageKit, NetworkManager, UPower, UDisks2, logind, timedated, hostnamed).

### Privilege
- S10. `hearthd` refuses to run as root.
- S11. `hearth-broker`: socket-activated, exits after 60 s idle; verifies caller via `SO_PEERCRED`; static method allowlist; destructive methods require polkit authorization of the calling uid, asked only after the call's params are validated (no password dialog for a request that would be refused); a request line must arrive within 5 s and at most 16 connections are served at once; every call written to the audit log; hardened unit (see below).
- S12. Docker via broker only, and only an API subset. The broker has no general container-create method: the UI can never create a container directly. Containers are created only by the stack mechanism in S12b. The S12 risks are `Privileged`, `CapAdd`, host PID/network/IPC namespaces, and bind mounts of `/`, `/etc`, `/root`, `/var/run/docker.sock`, `/proc`, `/sys`, `/dev`. They are refused except as S12b allows. (Viewing such existing containers is fine and flagged in Security posture.)
- S12a. Container exec shell (owner decision, 2026-10-27): broker method `docker.containers.exec` only. Fixed command `/bin/sh` (no caller-chosen command, user or env); running containers only; refused for any container with an S12 risk (privileged, added capabilities, host PID/network/IPC, risky bind mounts or the Docker socket), since a shell there is a host root shell; polkit `org.hearth.docker.exec` is `auth_admin` with no keep, so every session asks for the password; at most 2 sessions at once; start and end audited by the broker and by hearthd.
- S12b. Stack deployment (v1.5, owner decision, 2026-11-02). A stack is created only from a validated JSON spec. The broker strict-decodes it against closed lists at every level, refuses unknown keys, and regenerates a canonical compose file from the decoded value alone. Raw compose, YAML, anchors, extends, include, profiles, interpolation, `build`, `env_file`, `provider`, lifecycle hooks, `volumes_from`, `cgroup_parent`, `credential_spec`, a volume's `driver_opts`, non-local network or logging drivers, reserved labels and caller-supplied CLI flags never reach Docker. Compose runs in `hearth-stack@.service` with a fixed argv, no capability and no home. Never allowed, even with opt-in: `privileged`; binds of `/`, `/etc` or anything under them, `/var/lib/hearth` or `/var/lib/docker`; `security_opt` unconfined values; capabilities `ALL`, `SYS_ADMIN`, `SYS_MODULE`; raw disk, `/dev/mem` and `/dev/kmem` devices. Refused unless opted in per stack and per flag: other added capabilities, one by one; listed GPU, `/dev/net/tun` and similar devices; host network, PID or IPC; `userns_mode: host`; named sysctls; the Docker socket; binds of `/root`, `/proc`, `/sys`, `/dev`. Each flag is shown as a danger, needs `org.hearth.stack.danger` (`auth_admin`, no keep), is named in that dialog and in one audit entry per container, and appears in Security posture. One prompt covers a deploy or update. Binds must lie under roots the owner approved for that stack, after cleaning and link resolution, checked before polkit, again before `up`, and against the live mounts after `up`, by `hearth-pathcheck@.service` (only CAP_DAC_READ_SEARCH, no network), so the broker gains no capability and no view of home. A known limit: a link swapped between the check and the mount is caught only after `up`, which then stops the stack and reports it. Ports default to 127.0.0.1; any other address is a per-stack opt-in shown as exposure. A stack holds the same S12a position as any container: a container with an S12 risk still gets no shell.
- S12c. Stack secrets (v1.5): stored only in the stack's root 0600 `secrets.env` under a 0700 directory. A service receives only the keys its spec names, never the whole file. Values never appear in the journal, audit log, polkit messages, reports, exports or the import dry-run, and audit hashes cover key names only, because a hash of a weak password can be guessed. Revealing a value takes a click and `org.hearth.stack.secrets` (`auth_admin`, no keep). Hearth's inspect view hides every value a stack marks secret; `docker inspect` on the host still shows them to the docker group, which Hearth cannot prevent.
- S12d. Stack backups (v1.5): `stack.backup` and `stack.restore` have a fixed implementation with no script body: `tar --zstd` in units of their own with no network, archives root 0600 in a 0700 directory, the last N kept. A preview shows size first, and binds on external disks are excluded unless chosen. Restore is destructive (S15): a preview of what is overwritten, then a typed confirmation. A schedule is a generated timer that starts only the fixed unit, with a validated OnCalendar, so S13's script copy does not apply.
- S13. Root scheduled jobs: script copied to `/var/lib/hearth/jobs/<id>/run` owned by root mode `0755`; never executed from a user-writable path. Requires polkit.
- S14. Terminal runs as the user: hearthd opens the pty and passes only its fd to a transient unit of the user's systemd manager running the user's login shell (from passwd, if `/etc/shells` lists it); hearthd executes nothing, at most 8 shells at once, each opening audited. Never a root shell on the host from the UI (container shells: S12a only).

### Destructive actions
- S15. Preview/simulate first (apt simulate, Docker reclaimable size, file list), return a short-lived preview token; execute only with that token.
- S15a. Profiles (SPEC 18) run each step as its registered action, audited; a step that would need a typed confirmation (critical units, hearthd's own unit) is refused when the profile is saved and again when it runs, and apps are started but never closed (closing can lose unsaved work). Activating by hand previews what will change, with a token when anything stops. A profile may run unattended while a game runs only if the user turned that on for it, and then holds only user units and apps: a system unit or container may open a password dialog (`org.hearth.docker.control` is `auth_admin_keep`), which must not appear over a game or come to be expected without a click. Games are found in the command lines of the user's own processes, never their environment, and nothing of those is stored. Each automatic change is audited and shown in a desktop notification.
- S15b. Modes (v1.6) extend S15a, which still holds: apps are never closed. Mode files are untrusted and hold names, never commands or specs; they reach stacks only by name, through the broker methods of S12b. A trigger arms only by a click in Hearth, recorded in the database with the file's hash, and a changed file disarms it, so no file can arm itself. Automatic triggers use a non-interactive polkit check, so no dialog can appear, not even inside an `auth_admin_keep` window. A stack action that needs authorization becomes a notification the user clicks to approve. A Wi-Fi trigger matches a NetworkManager connection UUID, because anyone can broadcast an SSID. An unattended grant is per stack, approved once with `org.hearth.stack.grant` (`auth_admin`, no keep), stored root-owned, checked by the broker, stop only unless start is chosen, and expires after 90 days. Its risk is that anything reaching hearthd can stop those stacks without a password: an outage, not privilege.
- S16. Block removal of `Essential: yes` / `Protected: yes` / `Priority: required` packages and of Hearth itself, also when another change would take one along. Double confirm for critical units.
- S16a. Packages outside dpkg: snaps are removed through snapd (polkit); Flatpak, npm (user-owned prefix only), cargo and Go binaries by the manager's own uninstall (`gio trash` for a Go binary) run as a transient unit of the user's systemd manager, as the user and outside hearthd's sandbox, with a fixed argv built from the listing (validated names, no shell, no environment expansion). pip `--user` packages are listed, never removed (it would need `--break-system-packages`). Runtimes in use (and their extensions: GL drivers, codecs, Compat), system snaps, npm itself and root-owned prefixes are blocked.
- S16b. Holding a Debian package (PackageKit has no hold) is the broker's `pkg.hold`: polkit `org.hearth.packages.hold` (`auth_admin_keep`), then `apt-mark hold|unhold <name[:arch]>` through safeexec with the name validated before polkit is asked. The broker unit may write `/var/lib/dpkg` for it and still has no capabilities.
- S16c. Space advisor: sizes are measured unprivileged. The user's files go to the trash through `gio trash` (a transient unit of the user's manager, as S16a), at most 16 at a time; only what the advisor can list qualifies (direct, non-link children of the cache folder; regular files of the user's outside hidden folders), checked when previewed and again by device and inode when run, so a swapped path is not trashed. Emptying the trash deletes for good: the word is typed. Cleanups as root are two broker methods behind `org.hearth.space.clean` (`auth_admin_keep`): `apt.clean` takes no parameters, holds apt's own lock and removes only regular `*.deb` files of `/var/cache/apt/archives`, following no link; `journal.vacuum` takes one of four fixed sizes, never less than 100 MiB. The broker may write those two directories and nothing new otherwise, with no added capability. Old kernels go through package removal (S15, S16): the running kernel and the two newest are never offered.
- S16d. Service overrides: Hearth writes only `<unit>.service.d/hearth.conf`, never the original unit, and renders it from an allowlist of seven directives (MemoryMax, CPUQuota, Restart, RestartSec, Nice, IOWeight, TimeoutStopSec), each value shape-checked; no Exec*, Environment, User or paths, since those equal root. User units: hearthd writes `~/.config/systemd/user`. System units: one broker method, `unit.override`, params validated before polkit, polkit `org.hearth.units.override` is `auth_admin` with no keep, no capability added, then daemon-reload. Templates and Hearth's own units are refused; critical units need the typed confirmation. A link in place of the directory or file is refused. Purge removes the system drop-ins.
- S16e. Resource caps: `unit/cap` sets MemoryMax and CPUQuota on the user's own services and scopes through `SetUnitProperties` with runtime=true, so nothing reaches disk and a cap ends with the unit; critical units (session, dbus, Hearth) are refused, not confirmed. Disk priority is `ioprio_set` on the user's own processes, never the realtime class. Container limits are the broker's `docker.containers.update`: memory, CPUs and restart policy only (strict decoding, bounds checked before polkit `org.hearth.docker.control`); swap follows memory, and no other HostConfig field can be sent.
- S16f. Disk health: broker `disk.smart` (read-only, no polkit, so polling raises no dialog) and `disk.selftest` (polkit `org.hearth.disk.selftest`, `auth_admin_keep`, params validated first). One argv each through safeexec, `smartctl -j -a -n standby /dev/<disk>` and `smartctl -j -t short|long /dev/<disk>`; the name must match a whole SATA/SAS/NVMe disk and be listed in `/sys/block`, so partitions and paths are refused. `-n standby` never wakes a sleeping disk. Only the fields Hearth shows leave the broker, never serial numbers or WWNs, and disk-supplied strings are cleaned of control characters. A self-test keeps the data; abort and other `smartctl` options are not reachable. This is the one reason the broker unit holds capabilities: CAP_SYS_RAWIO (ATA) and CAP_SYS_ADMIN (NVMe), with PrivateDevices replaced by a closed device policy that opens disks only.
- S16g. Restart needed: `/run/reboot-required` and the kernels in `/boot` are read unprivileged. Which services run old libraries takes reading other users' `/proc/<pid>/maps`, so it is `hearth-needrestart.service`, a static oneshot of its own: `needrestart -b -r l` (lists, never restarts), only CAP_SYS_PTRACE and CAP_DAC_READ_SEARCH, no network, read-only system and home, private devices, output to a file in the root-only state directory. The broker gains no capability: `system.needrestart` takes no params, needs no polkit since it changes nothing, starts that one unit at most every 5 minutes and returns validated unit names and cleaned session lines. Output without needrestart's version line is a failed run, never "nothing to restart". needrestart is a Suggests: its apt hook changes what an upgrade does.
- S16h. Closed broker methods added by v1.2–v1.3: fixed argv through safeexec, params validated before polkit, no new capability unless justified in the unit file. Battery charge threshold (`charge_control_end_threshold`, only when UPower cannot set it): accepts only 50–100, for a name listed in `/sys/class/power_supply` as a Battery that has the file, checked before polkit `org.hearth.battery.threshold` (`auth_admin_keep`), opened without following links; the broker unit may write `/sys/devices` for it, with no added capability. Lynis: only if installed, on request or a schedule the user sets. `lynis.run` takes no params and starts one oneshot, `hearth-lynis.service`, whose unit file holds the whole argv (`lynis audit system --cronjob --no-log --report-file ...`); polkit `org.hearth.lynis.run` (`auth_admin_keep`). It is a unit of its own as in S16g, so the broker gains no capability: only CAP_DAC_READ_SEARCH, CAP_SYS_PTRACE and CAP_NET_ADMIN (without which firewall rules cannot be listed), read-only system and home, and AF_UNIX and AF_NETLINK only, so no internet socket can be opened and nothing leaves the machine. Debian's profile already skips Lynis's update lookup. `lynis.schedule` picks off, weekly or monthly from a fixed table, under the same polkit action, and writes only `hearth-lynis.timer`, which purge removes; a scheduled run asks nothing, since the user authorized it once. `lynis.report` takes no params, needs no polkit and starts nothing: it reads the report (4 MiB bound, 500 findings each, 400 characters a field), a run's root-only file that replaces the last only after success, and passes on only the index, the Lynis version and cleaned findings, never the hostname, users or packages the file also lists. A report without its end line is a failed run, never a clean machine. hearthd stores only the figures of each run. ufw: `ufw.rule` takes only an action (allow or deny), proto (tcp or udp), port and optional source address or CIDR, canonicalized, with strict decoding before polkit; `ufw.set` takes on or off. Both use `org.hearth.firewall.manage`, `auth_admin` with no keep, since an opened port faces the network. As in S16g the broker gains no capability: it writes one line of validated words to a root-only file and starts the static `hearth-ufw.service`, whose `ExecStart=/usr/sbin/ufw $UFW_ARGS` is split by systemd with no shell; only that unit holds CAP_NET_ADMIN and CAP_NET_RAW, and it may write only `/etc/ufw` and `/run` (ufw's and iptables's locks live directly in it). Rules are added or deleted only while ufw is active, and a rule goes by its full text, so a number that has moved cannot delete another. Only plain inbound port rules can be changed; limit, logging, app, interface, outbound and route rules are shown read-only. `ufw.state` takes no params, needs no polkit and runs nothing: it reads ufw's own files, bounded (1 MiB, 1,000 rules). Every change has a preview (S15) that warns before cutting off SSH; enabling is allowed, disabling needs the words typed; nftables rule sets are read-only. Compose update (owner decision, 2026-11-02): hearthd renders `docker compose config --format json` as the user, one fixed shape through safeexec, because the broker cannot read home and a file read as root could quote root's files into a container. The rendering is offline: safeexec sets `COMPOSE_EXPERIMENTAL_GIT_REMOTE=0` and `COMPOSE_EXPERIMENTAL_OCI_REMOTE=0`, since by default a remote `include` or `extends` fetches from git or an OCI registry while rendering; the process environment wins over the project's `.env` (checked on Compose v5.6). The import dry-run (v1.5) renders the same way. The broker treats the rendering as untrusted: 40 KiB at most, closed lists of keys at every level, so everything S12 names is refused along with anything unknown, including `provider` (runs a host binary), `build`, lifecycle hooks, `devices`, `security_opt`, `sysctls`, secrets and configs from files, a volume's `driver_opts` (a bind mount by another name), and network and logging drivers beyond the local ones; bind sources must be absolute, clean and not risky. The same check runs for the preview and again before polkit. The value is marshalled again before use, so no duplicate key reads differently to Compose. Only an existing project: a service with no container is refused. `compose.update` uses `org.hearth.docker.compose`, `auth_admin` with no keep. Compose runs from that file in `hearth-compose.service`, no capability, Unix sockets only, no home, so it never sees the project's files; `up --pull always --no-build`, and the daemon does the pulling. A known limit: a bind source that is a link is resolved by the Docker daemon, and the broker cannot see into home to follow it, so a link to `/etc` passes the check; this needs the owner's password and a user who can already edit the project. Compose records its input file in its labels, so Hearth adds `org.hearth.compose.dir` and `.files` with the project's real places; `docker compose ls` shows the broker's file after an update.
- S16i. Integrity watch: runs as the user, needs no broker and only reads, apart from its own baseline in the database. Home items open through `os.Root`, so no link leads out of the home, and links are compared by target, never followed; a file's content is read bounded (64 MiB hashed, above that size and times; 2,000 entries, depth 4). An unchanged file is skipped by size, mtime and ctime, and ctime defeats a restored mtime. Folders in `/etc` are listed by name, never opened, and a folder the user cannot read is reported as such, not as empty or removed. The baseline's text exists only for small text files, never for one holding a private key, and is masked before it is stored: a line matching S19's words is replaced, after long base64 runs are set aside so a public key stays readable. A hidden line's change is still a change, and the page says it cannot show it. The diff route looks a path up among watched items, so it cannot read anything else. Accepting names path and hash as shown, so a newer change stays pending, and each accepted item is audited first. Alerts carry only the fixed watched item, never a file's content or the user's name. The first scan trusts what it finds, and the page says so; this detects later changes, and it cannot stop a process running as the user from editing the database.
- S16j. Access: runs as the user and only reads, with no broker. SSH logins come from `journalctl-ssh`, one fixed argv but for the start time, matching `_UID=0` as well as sshd's identifiers: the journal sets `_UID` itself, so a user cannot forge a login with `logger`. Without the system journal the page says so, never "no logins". Log lines are read from the end, since the user name in them is what a stranger typed and could pose as a source; the source must be an IP address or a plain host name, and user names are dropped, because people type passwords at login prompts. Accounts come from `/etc/passwd` and `/etc/group`, bounded; `/etc/shadow` is never opened and the GECOS and home fields are not read out. A member of `sudo` or `docker` without a passwd entry is still flagged. Sessions come from logind's own read methods over D-Bus. All strings are cleaned of control characters and shown as text.
- S17. Files go to the XDG trash (`gio trash` semantics) instead of unlinking, where applicable.
- S18. Audit log: append-only table (time, origin, uid, action, target, params hash, result). Viewable in the Change timeline.

### Secrets & data
- S19. Mask env values whose key matches `(?i)(pass|pwd|token|secret|key|auth|cred)`, and from v1.5 whose key ends in `_URL`, `_URI` or `_DSN` or whose value is a URL holding user info, since those often carry a password; reveal only on explicit click, never in logs, reports or exports.
- S20. DB, config and token files mode `0600`, dirs `0700`.
- S21. Health checks (Homepage): only user-entered URLs, `GET/HEAD`, 5 s timeout, max 1 redirect to the same host, no credentials unless the user configured them, response body discarded after 64 KiB.
- S21f. Hearth's own backups. Database copies: `VACUUM INTO` a temporary name, mode 0600 in a 0700 directory under the data directory, then renamed, keeping the last 4; only files matching Hearth's own name pattern are ever removed. They hold what the database holds, which by S20 and S21d is no channel secret or token. Settings file: a closed list of preferences, alert rules, Homepage tiles and profiles (modes from v1.6, whose triggers import disarmed); never channels, the session token, history or state. Tile addresses lose query parameters and fragments matching S19, uploaded icons stay behind, and a profile's game trigger is neither exported nor accepted, so a file cannot arm anything that runs alone; the preview shows each tile's cleaned address, since a health-checked tile makes Hearth fetch it. An imported file is untrusted: format and version checked, unknown fields refused, 512 KiB and 512 entries per section at most, and every entry goes through the validator its form uses, so a refused entry is shown with its reason and is not applied. Import is a destructive action (S15): it adds and replaces by name and deletes nothing, an active profile is not changed, and it makes a database copy first or changes nothing. Removal, restore and download of copies are not offered through the API.
- S21d. Alert channels (ntfy, mail): settings and secrets live in `$XDG_CONFIG_HOME/hearth/channels.json`, mode `0600`, not in the database, so no database copy or backup can carry them; the API never returns a token, password or ntfy topic (on a public server the topic is the password), an empty form field keeps the saved value, and the audit log records only which channels are on. ntfy: HTTPS only, `https://host[:port]` with no path or user info, TLS 1.2+, certificates verified, published as JSON to the server root so no system string reaches a header, 5 s timeout, no redirects, no proxy, reply discarded after 64 KiB. Mail: implicit TLS or STARTTLS, nothing else; certificates verified against the host name; a server that offers no STARTTLS gets no name, password or address; 10 s timeout; one validated recipient; subject cleaned and encoded so nothing can add a header. What leaves the machine: the rule's name and severity and the instance (disk, container, unit, mount). Errors name the step, never a URL or a server's reply. Log-pattern rules (RE2, at most 200 characters and 4,000 compiled instructions, never one that matches an empty line, at most 16 enabled) read the journal only while one is enabled; each line is bounded to 4 KiB; an incident stays open until 10 minutes pass without a match, so a flood is one notification; the matching line is never stored, logged or sent, and neither is the pattern.
- S21a. Image update check (Docker images): only when the user asks; HTTPS only; anonymous pull tokens from the registry's Bearer challenge (HTTPS realm only), never the user's Docker credentials; manifest HEAD/GET only, 10 s timeout, redirects only within the host, bodies bounded (manifest 4 MiB, token 64 KiB).
- S21b. Homepage suggestions: only when the user asks; only this machine's own listeners (from `/proc/net/tcp*`) and published container ports, never hearthd's own port or known non-HTTP ports, at most 64 probes, 8 at a time; one `GET /` each, 1.5 s timeout, no redirects followed, no proxy, credentials or cookies, body discarded after 64 KiB; the page title is plain text (escaped in the UI). Nothing is saved without the user saving the form.
- S21c. Known CVEs (Security posture): `debsecan`, only if installed and only when the user asks; one fixed argv through safeexec (`--suite <codename from /etc/os-release> --format summary`), 2 min timeout, output bounded (1 MiB). debsecan fetches the Debian security tracker's public data over HTTPS; nothing about the machine is sent but the release name in the URL. The run is audited; its result is kept in the settings table.
- S21e. Automatic updates (Security posture) are read, never changed: one fixed argv through safeexec, `apt-config shell` for the two `APT::Periodic` keys and nothing else, so proxy credentials in the APT configuration never reach Hearth; the last run is the mtime of apt's stamp file. No broker method, no polkit.
- S21g. Outbound (v1.2): no new listener, and nothing leaves the machine except what the user configures (ntfy/SMTP, health-check URLs, connectivity targets). External tools (lynis, fwupd data, needrestart) are used only if installed, and only when the user asks or a schedule they set runs.
- S21h. Connectivity checks (v1.2): TCP connect, or unprivileged ICMP if `ping_group_range` allows; never raw sockets.
